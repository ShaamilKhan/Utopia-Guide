About this guide

This guide explains the whole Utopia app from top to bottom. It covers what the app does, what it is built with, how it is put together, and how each part works inside. It is written for someone studying the app. They may know some programming, but have never seen this code. Technical words are explained the first time they appear, and there is a glossary at the end.

Everything here was checked against the source code at the time of writing. If this guide and the code ever disagree, the code is right. A few recent changes have not been tried on a real phone yet. Those places say "not yet tested on a phone", and it means exactly that.

Chapter 01·Overview

What Utopia is#

Utopia is a personal music player, mainly for Android phones, that also runs in a desktop or phone web browser. It brings several music sources together in one place:

  • YouTube Music: search, albums, artists and "radio" (endless similar songs). This is the main source.
  • Jamendo: free, Creative-Commons-licensed music, offered in search when YouTube has nothing.
  • Your own audio files: files picked from the phone and added to playlists.
  • Navidrome: a self-hosted music server. The support code exists, but no screen uses it yet.

You sign in with Google. Your likes, playlists, play history and listening stats then follow you to every device where you sign in.

Ground rules behind every decision

Zero running cost, low maintenance

Utopia has no server of its own. The only online service it owns is Firebase, on Google's free tier, used for sign-in and a small cloud database. Everything else happens on the device, or talks directly to public music and lyrics services.

It has to behave like a real music player

Songs must keep playing in order with the screen off or locked and the app in the background. The notification must show each song's cover. Android must not close the app. Much of the Android engineering in section 7 exists for this reason.

A settled look

"Retro" means colour and a script typeface, never vintage clutter. The one deliberately realistic decoration is a black vinyl record with the album art as its label.

Chapter 02·Overview

The big picture#

Utopia is a web app inside a native shell. The screens are ordinary web technology (HTML, CSS, TypeScript with React). On Android, a tool called Capacitor wraps them in a native app that shows them in a built-in browser view (a WebView). Capacitor also lets that web code call native plugins: pieces written in Kotlin that can do things a web page cannot, such as playing audio as a proper background media service.

There are two halves:

  • src/ui/ is what you see: screens, the player, menus and styles.
  • src/core/ is the logic. It never imports UI code. Each area keeps its data in a store, a small shared state container from the zustand library. The UI reads a store and re-draws when it changes.

Most features are written once. The phone layout and the desktop layout are two "shells" around the same screens.

Chapter 05·Overview

What happens when the app starts#

src/main.tsx, in order:

  1. Load the theme colour tokens and base styles. Apply the saved theme (initTheme).
  2. Start the history observer, which records plays as the player reports them.
  3. Start the Firebase sign-in listener. If Firebase isn't configured, the app runs in local-only mode.
  4. Android only:
    • handle music.youtube.com/watch links opened with Utopia;
    • apply the saved screen refresh rate and start watching phone temperature.
  5. 20 seconds later, tidy the response cache.
  6. Draw <App/>.

src/App.tsx then chooses which screen to show from the sign-in state:

StateScreen
Sign-in still loadingBoot screen: wordmark, spinner, a random playful line ("Waking up the vinyl…"), credit "Made by Shaamil Khan A"
Signed outSign-in screen: "Sign in with Google"
Signed in, cloud data not yet confirmedBoot screen stays up (the "hydration gate", section 12)
Cloud pull failedSync-error screen: "We couldn't restore your account data yet." with Try Again / Sign out
New account, nothing to restoreOnboarding: pick a name (max 32 characters) and one of six avatar colours
Offline but with downloadsThe app opens anyway, so downloaded music still plays
Firebase not configuredOnboarding once, then the app, fully local

The app also picks a shell: the phone layout on the Android app or any window 639 px wide or narrower, otherwise the desktop layout. Only the shell in use is downloaded.

Using the app: every feature#

6.1 The two layouts#

Phone (MobileShell):

  • From the top: an offline banner (when needed), the current screen, a floating mini player, and a bottom tab bar with Home, Library and Discover. Discover uses a magnifier icon because search lives there.
  • Every screen header has two round buttons at the right: Stats (a bar-chart icon) and your profile picture, which opens Settings. The profile picture is always the rightmost.

Desktop (DesktopShell):

  • A slim 52 px sidebar holds your avatar, Home, Library, Discover and a gear icon.
  • The main panel sits beside it, with a floating player pill centred at the bottom.
  • The gear opens a small settings popover with theme swatches, your account name and Sign Out.
  • The full Stats page and Settings page are phone-only for now (see section 19).

Both layouts use the same screens and overlays. A screen is built the first time you visit it and then kept, so switching tabs keeps your scroll position.

6.2 Home#

  • Greeting by time of day ("Good morning / afternoon / evening"), with your name in the script face.
  • Album rail: up to 10 albums from your top three artists, mixed so no one artist dominates. It is titled "More of your top artists", or "Featured Albums" for a new user. Each card has a vinyl record peeking out of the sleeve.
    • On desktop, hovering slides the record up.
    • On the phone, a press and hold does the same.
  • Following Artists: round photos of the artists you follow. Tap one to open the artist page. It falls back to your top artists when you follow nobody.
  • Continue Playing: songs you played recently (not the queue), up to 12.
    • Two rows per page on desktop, four on the phone. Swipe or use the arrows to change page.
    • Each row has play/pause, a heart and a "⋯" menu.
  • Recommended for you: a 3×3 grid of 9 personalised songs (section 10). Liked songs and songs you marked "Don't suggest" are left out.
  • There is also a small personalised easter egg tied to one profile name (see HomeScreen.tsx).

6.3 Discover and search#

  • Search box ("Artists, songs, albums…"). Searching starts 0.4 s after you stop typing.
    • It queries YouTube Music for 12 songs and 6 albums at once.
    • If an artist's name closely matches your text, an artist shortcut card appears. The match ignores capitals and punctuation, so "AC/DC" matches "acdc".
    • Only when YouTube finds nothing is there a button to search Jamendo instead.
  • Browse Genres: 4 chips chosen from 14 genres, ranked by your taste and fixed for the day.
    • A chip loads a personalised 20-song mix for that genre.
    • Tapping the selected chip again shows Trending Now.
  • Tapping a song from here starts radio play: that song, then about 20 similar songs added automatically.

6.4 Library#

In order:

  1. Your Playlists, with a "+ New Playlist" button. The first card is always Liked Songs, a playlist built from your hearts, newest first.
  2. Most Played: your top 6 songs by play count.
  3. Top Artists: up to 8 artists, with photos and play counts.
  4. Downloads: a wide card with a collage of downloaded covers, "N tracks available offline". It opens "Downloaded Songs".

  5. Recently Played: 6 recent songs.

6.5 Album and playlist page#

A full-screen overlay. It closes with ×, a tap outside, Escape or Android back.

    • Play All and Queue All.

  • Track rows: number (or animated "playing" bars), cover, title, artist, play count, duration, play/pause and "⋯". Your own playlists also show × to remove a song.
  • Recommended songs: a playlist with fewer than 9 songs shows suggestions with a "+" to fill it up.
  • Liked Songs and Downloaded Songs are virtual lists. They have no delete, remove or cover buttons.

6.6 Artist page#

  • A banner photo, avatar and name.

6.8 Playlists and their covers#

  • Create a playlist from Library or from a song's menu. The dialog has:
    • an optional cover photo;
    • a name (max 60 characters);
    • Add local files;
    • a picker of up to 16 suggestions (your liked songs, then recent plays).
  • Edit a playlist: add or remove songs, add files, and change or remove the cover.
  • Cover rules, in order:

6.9 The player#

Mini player (phone):

  • A "record deck" card above the tab bar. A spinning record with the cover as its label sits on the left, next to the title, artist, a thin progress line, and previous / play-pause / next.
  • Tap the card to open Now Playing.
  • The status line can read "Buffering…", "Waiting for connection…" or "Playback error".

Player pill (desktop):

  • Previous / play / next, a round cover with the title, "⋯", Lyrics, Queue, and mute with a volume bar.
  • The arrow keys change the volume.

Now Playing (full screen):

  • The record: a big black vinyl disc with the album art as its label. It spins while playing.
  • Scratching: double-tap the disc, hold, and drag around it to scrub through the song.
    • The seek bar follows your finger, and the jump happens when you let go.
    • On first use after installing, a one-time hint explains the gesture ("Double-tap the disc and hold, then drag around it").
  • Controls:
    • A heart, and a tag for the song's source.
    • A draggable seek bar with times.
    • Shuffle, previous, play/pause, next, and repeat (off → all → one, with a "1" badge).
  • Actions:
    • Share: the phone's share sheet, with a music.youtube.com link.
    • Sleep timer: 10, 15, 30, 45, 60, 80 or 100 minutes, with a badge showing minutes left.
    • Lyrics and More (the song menu).
  • Lyrics (section 9):
    • With word timing, each word fills in as it is sung. With line timing, the current line grows and stays centred. Tap a line to jump there.
    • A badge names the mode ("Word sync", "Line sync" or "Lyrics") and the provider.
    • On the phone, lyrics replace the record and title in place, leaving a small cover-and-title header above the controls. On desktop, lyrics sit in a permanent column beside the controls.
  • Up Next (queue):
    • Drag handles reorder songs (the list scrolls near the edges). Tap a row to play it.
    • Clear empties what's coming while the current song keeps playing.

Volume toast: a small on-screen indicator that appears for about 1.5 seconds when the volume changes.

6.10 How the queue behaves#

  • The priority block. "Add to Queue" puts songs in a block right after the current one, in the order you added them. When the block runs out, the list you were playing continues.
  • Play Next goes to the very front of that block. Queue All adds a whole album or playlist as one block.
  • Swipe to queue (phone): swipe a song row sideways to add it to the queue. A short vibration confirms it.
  • Shuffle reorders only the songs still to come, and turning it off restores the original order.
  • Repeat one loops the current song.
  • Previous: the first tap restarts the song; a second tap within 3 seconds goes back a song.
  • Where you tap decides what plays:
    • a song in an album, playlist or artist list plays that list in order;
    • a song anywhere else starts a radio of similar songs.
  • Radio tops up when 3 or fewer songs are left, so music never just stops (section 10).

6.11 Downloads#

  • Download saves a song for offline listening, with its cover and its lyrics when they can be found.
    • On Android the audio goes into the phone's shared Documents/Utopia Music folder, so you can see it in the Files app.
  • Downloaded Songs in Library lists everything saved.
  • Offline, a banner says "No internet connection · downloaded music still works".
  • After a reinstall, Utopia rebuilds the list from the folder. See section 8.

Chapter 07·Engine

How playback works#

This is the heart of the app, and the most engineered part.

7.1 Songs and sources#

  • A Track (src/core/types.ts) describes one song:
    • an id prefixed by its source (youtube:<videoId>, jamendo:1234, local:…);
    • title, artist, album, duration and artwork;
    • source and streamUrl.
    • For YouTube, streamUrl is only a placeholder (ytm:<videoId>). The real link is fetched just before playing.
  • Sources (src/core/sources/) implement a small MusicSource interface: search, plus optional radio, artist and stream lookup.
    • YouTube (youtube.ts) sends hand-written requests to YouTube Music's internal API.
      • It parses results defensively, so a play count is never mistaken for an artist name.
      • It remembers recent answers for a few minutes.
    • Jamendo (jamendo.ts): its audio links are permanent, so no resolving step is needed.
    • Navidrome (navidrome.ts) speaks the Subsonic API with a salted password token. It is not yet used by any screen.
    • Local files (playlist/localFiles.ts): on Android, a picked file is copied into the app's storage so it keeps working after a restart.

7.2 The player store (src/core/player/store.ts)#

This store holds the queue: the song list, the current position, the priority block, shuffle order, repeat mode, the sleep timer, and the recent-songs trail used by "previous".

playCurrent() is the single path every song start goes through:

  1. Give the request a number, so a slow, outdated load can never start playing over a newer one.
  2. Show "buffering".
  3. A downloaded file always wins.
  4. Otherwise pick an engine (7.3) and, for YouTube, resolve a playable link (7.4).
  5. Load and play.
  6. In the background, send the next 60 songs to the Android service (7.5), so it can move on by itself with the screen off.

The queue is saved on the device, as the song list plus a small, frequently updated position checkpoint. After a restart it comes back paused. If Android's playback service is still playing when the app is reopened, the app adopts that playback instead of showing an older saved state.

7.3 Engines#

An engine is the thing that actually makes sound. All engines implement the same AudioEngine interface: load, play, pause, seek, volume.

EngineWhereHow
NativeAudioEngineAndroid, every sourceA thin proxy to the native Media3 service
Html5AudioEngineWeb, for files/Jamendo/NavidromeA single <audio> element
YoutubeIframeEngineWeb, for YouTubeYouTube's official embedded player, hidden

On Android, every source goes through the native service. That way one playlist can cross from a YouTube song to a local file to a Jamendo song with the screen off, with no JavaScript involved.

7.4 Getting a playable YouTube link (youtubeResolve.ts)#

YouTube doesn't publish audio links. The app uses youtubei.js, an open-source client for YouTube's internal API, to ask for a song's streams. It picks the best audio-only track (MP4 audio by preference) and deciphers its protected link by running YouTube's own player JavaScript locally. The result is a signed link on googlevideo.com, YouTube's media CDN. The link expires after a few hours and is tied to the identity and network that asked for it.

The chain, on Android:

  • BotGuard and PoToken. BotGuard is Google's anti-bot check. It runs JavaScript that only a real browser engine can execute. Solving it produces a "proof of origin" token, the PoToken. The PoTokenPlugin (section 14) runs this in an invisible WebView and returns two tokens:
    • one for the request itself;
    • one added to the audio link as pot=.
  • Identity must match. The browser identity (User-Agent) presented when asking for the link must match the one used to download it, and the one the PoToken was made under. So the app keeps two separate youtubei.js sessions with fixed identities, and each link carries the User-Agent it was made with.
  • Deadlines, so a stuck step never hangs playback: 45 s for the request, 60 s to get a session, 90 s overall.
  • Sessions are rebuilt after 12 hours or after a failure.
  • YouTube's decoding data is cached so it isn't fetched again for every song.
  • If a signed link is later refused mid-song (HTTP 403), the app retries that song through the IOS client.
  • On the web this chain doesn't play. Browsers block these links (see section 19), so the web uses YouTube's embedded player instead.

7.5 The Android playback service (NativePlaybackPlugin.kt)#

A foreground service is a part of an Android app that Android treats as "the user is using this". It must show a notification, and in return Android doesn't stop it in the background. Music apps like Spotify and YouTube Music rely on exactly this.

Utopia's NativePlaybackService is a Media3 MediaSessionService. It owns:

  • ExoPlayer, which holds the whole upcoming playlist;
  • the notification and lock-screen controls, each showing the song's cover;
  • audio focus, so it pauses for calls and other apps;
  • the foreground state. Registering the media session (addSession) is what makes Media3 promote the service. Before that fix, Android stopped the app about a minute after it was hidden.

What the app (JavaScript) does:

  • keeps the queue;
  • fetches links (resolves YouTube songs);
  • sends the next 60 songs to the service. Each list is tagged with the song it was built for, so a list that arrives late is ignored. It is passed inside the app process rather than through Android's IPC, which had a size limit that crashed on long queues.

What the service does:

  • moves from song to song by itself, with the screen off;
  • tells the app afterwards, through events such as trackChanged, ended, error and networkChanged.

Keeping the queue in order:

  • A song whose link fails temporarily keeps its place. The list sent to the service stops just before it, and the app keeps retrying.
  • Songs that can never play are skipped. Skipping is limited to 5 in a row.
  • On a player error, the service waits 10 seconds for the app to repair that song's link before skipping it.

Keeping links fresh:

  • A link is reused until 30 minutes before it expires.
  • The next song's link is re-fetched at every song change, whenever the phone switches network (Wi-Fi ↔ mobile data), and whenever the service reports the next link was refused.

How audio travels from the internet to your ears:

The file size is given to the cache in advance. Without it, googlevideo's roughly 1–2 MB chunks looked like whole songs, and playback cut off after about a minute.

Extra behaviour:

  • Swipe-away: swiping the app away while music plays keeps the service playing.
  • Sleep timer: enforced by the service too, so it works with the screen off.
  • Renderer crash: if the WebView behind the UI crashes, a patched MainActivity rebuilds only the UI, and the music keeps going.

7.6 Power and heat#

These are ideas from Android's Media3 guidance and from studying other players (Echo, ViMusic, Metrolist, InnerTune), aimed at a cooler phone and longer battery life:

  • Audio offload. Decoding is handed to the phone's low-power audio chip, so the main processor can sleep between refills.
    • A watchdog turns offload off for that exact Android build if it ever stalls.
    • It is retried automatically after an OS update.
  • Burst buffering. The player downloads 1–5 minutes of audio in one go, then lets the radio sleep, instead of trickling data constantly.
  • Wake locks, used sparingly. A wake lock keeps the processor (or Wi-Fi) awake with the screen off. Utopia holds each one only as long as needed, with a time limit: | Lock | Up to | Why | |---|---|---| | Handoff | 60 s | The app starting the next song itself (end of list, retries) | | JS work | 30 s | The app refreshing links after a song or network change while hidden | | Load | 5 min | A download burst, which offload's sleep would otherwise throttle | | Artwork | 20 s | Fetching the notification cover with the screen locked |
  • Fewer wake-ups:
    • While visible, progress updates come every 250 ms, or every 1 s when the phone is hot.
    • While hidden and playing, the service checks every 10 s but wakes the app only every 30 s.
    • When hidden and paused, nothing runs.
  • Screen: a refresh-rate choice (60 Hz uses less power than 120 Hz), and heat mode, which pauses decorative animation (6.14).
  • Maker battery killers. Some makers' battery managers stop apps even while they play music. Settings links straight to each maker's screen, and a one-time dialog asks Android to exempt Utopia from battery optimisation.

7.7 Walk-through: from a tap to the next song with the screen off#

  1. 1

    You tap a song on Home. Radio lookup and playback start together.

  2. 2

    playCurrent() takes the 60 s handoff lock, shows buffering, and picks the native engine.

  3. 3

    Resolve

    • the PoToken plugin mints tokens;
    • youtubei.js asks as YouTube Music and picks the best audio format;
    • the link is deciphered and pot= added (the IOS client is used if that fails).
  4. 4

    Load the service receives the link, its User-Agent, a cache key and the file size, and ExoPlayer prepares it.

  5. 5

    Play ExoPlayer streams through OkHttp, and sound starts after about 1 s of buffer. Media3 posts the notification with the cover and promotes the service to the foreground.

  6. 6

    Bookkeeping

    • the play is recorded in history and lyrics are warmed;
    • radio songs arrive and are added;
    • the next 60 songs are sent to the service.
  7. 7

    Screen off

    • updates slow down;
    • ExoPlayer downloads a burst and offload lets the processor sleep;
    • the next song is pre-loaded (long songs are pre-cached separately).
  8. 8

    The song ends ExoPlayer moves to the next song by itself, and the notification updates with its already-loaded cover.

  9. 9

    The app catches up when it next runs:

    • it records the finished song;
    • it moves its own position forward;
    • it refreshes the new "next" song's link;
    • it tops up radio if 3 or fewer songs remain.

Chapter 08·Engine

Downloads and offline listening#

Saving a download#

  1. For YouTube, resolve a link (7.4). If the server refuses it, retry through the IOS client.
  2. Fetch the whole file with completeMediaFetch.ts.
    • It uses repeated "give me bytes N onward" requests, each overlapping the last chunk by 64 bytes to catch servers that ignore the requested range.
    • The download must prove it is complete, from the reported size, the clen value in the link, or the server's range headers. A truncated song is never saved.
  3. Write the audio:
    • on Android, to Documents/Utopia Music/Artist - Title [id tail].m4a, so it shows in the Files app and survives uninstalling Utopia;
    • on the web, to private app storage.
  4. Save the extras in private app storage: the cover (max 3 MB) and the best lyrics found. Missing lyrics are retried after a day.
  5. Record the song in the downloads list (utopia-downloads-v1 in local storage).

A download counts as done only when the audio, the cover and the lyrics (if any exist) are all saved.

Getting downloads back after a reinstall#

Uninstalling Android apps wipes their private storage. That includes the downloads list, but not the songs in Documents. Before 1.2.4, a reinstall therefore showed 0 downloads over a folder full of songs. Now the folder is the source of truth:

  • Every launch scans Documents/Utopia Music, and any audio file without a list entry gets one back.
  • Matching a file to its song. The file name carries the end of the song's id, e.g. [tube_Umqb9KENgmk].
    • YouTube and Jamendo ids survive whole, so the song keeps working as a real YouTube or Jamendo track: radio, likes and lyrics all work.
    • Title and artist come from the file name at first.
    • When your synced history, likes or playlists know that song, the entry is upgraded to the full details (album, duration, the real cover). It usually happens a few seconds after sign-in.
    • A file with an unfamiliar name still appears, as a plain local song.
  • Android's ownership rule. Android gives each file in shared storage to the install that saved it. A new install can only see the older files with the "Music and audio" permission:
    • Utopia asks for it once, the first time you open Library on a new install, and only if the folder exists.
    • If you said no, Library shows Find on phone. If Android no longer offers the dialog, it shows Allow in Settings, which opens Utopia's system settings page, and Utopia rescans when you come back.
  • Deleting a restored song. A file saved by an earlier install can only be deleted after you confirm in Android's own "Allow Utopia to delete…?" dialog. If you decline, the song stays in the list rather than coming back on the next scan.
  • Name clashes. If a new download's file name is taken by a file this install can't replace, it is saved beside it as … (2).m4a.
  • Deleted in the Files app. A song you deleted there disappears from the list on the next scan, but only when Utopia has the music permission. Without it, hidden and deleted look the same, so nothing is removed.
  • Covers and lyrics were kept in private storage, so they are re-downloaded automatically the next time you're online.

Not yet tested on a phone

It is covered by an automated simulation of Android's folder rules (section 18).

Playing a download#

Downloads always win over streaming. On Android the service reads the file directly, and uses the cover saved with it for the notification, so it needs no network at all.

Chapter 09·Engine

Lyrics#

resolveLyrics(track) (src/core/lyrics/) tries providers in order and uses the best timing that is honestly available. The app never fakes timing.

  1. Better Lyrics: Apple-style TTML with real per-word timing.
    • Accepted only if every line has word timing.
    • Used on the Android app (browsers can't reach it).
    • Cached for 30 days.
  2. LRCLIB: line-by-line timestamps.
    • It tries an exact lookup (artist, cleaned title, album, duration), then searches, and scores the matches.
    • An instrumental shows "♪ Instrumental ♪".
  3. YouTube Music: plain text with no timing, for YouTube songs only.

Where lyrics are read from, in order:

  • a downloaded song's saved lyrics;
  • a small recent-lyrics cache (hits kept 14 days, misses 1 hour), warmed when a song starts;
  • a fresh lookup.

Chapter 10·Engine

Personalisation: history, taste, recommendations, stats#

History#

  • A play is recorded when a song starts, and finalised with how much you heard when it ends or you skip.
  • The last 600 plays are kept, plus a lifetime play count.
  • History syncs lazily, in batches (section 12).

Taste (user/taste.ts)#

computeTaste scores artists, genre tags and languages:

  • Recency: each play counts less the older it is, halving every 14 days.
  • How much you heard:
    • under 20% counts for nothing;
    • 20–50% counts a little;
    • more counts almost fully.
  • Likes add a fixed boost to the artist, tags and language. Follows add a bigger boost to the artist.
  • Repeat bonus: an artist gets up to +90% for being played on several different days. A one-day binge fades away instead of skewing your recommendations for weeks.
  • Language is detected from the script (Devanagari, Tamil, Hangul, …) plus a few romanised word hints.

Recommendations and radio (user/recommendations.ts, player/radio.ts)#

  • Radio for one song (getSimilarTracks):
    • YouTube's "Up next" list, plus a search anchored on the song's title, artist, tags and language;
    • compilations, DJ mixes, very long tracks, and songs whose language or genre clash with the song are filtered out;
    • duplicates are removed.
  • Personalised picks (Home, the Discover genre mixes, playlist suggestions):
    • up to 3 seed artists you love, varied, whose radio gives "familiar" songs;
    • two exploration searches built from your languages, tags and artists;
    • the pools are mixed together.
    • Liked songs, dismissed songs, and your 6 most recent and 6 most played songs are left out.

Listening stats (user/listeningStats.ts)#

  • Plays are rolled up per month. Each month holds:
    • plays and minutes;
    • an hour-of-day chart, a weekday chart and minutes per day;
    • top songs, artists and albums.
  • Every song and artist heard is also kept as a short fingerprint (a hash), so "songs" and "artists" counts stay exact after the top lists are trimmed.
  • Each device writes only its own section, and the display adds the devices together. Two phones therefore never double-count.
  • Plays from before stats existed were rebuilt once from history.
  • The summary computes:
    • totals and averages;
    • top-5 lists;
    • the longest streak and the top day;
    • new artists;
    • the peak hour and persona;
    • the comparison with the previous period.

Chapter 11·Engine

Artist photos and caching#

  • Artist photos come from Deezer first (an exact or close name match), with the YouTube channel header as a fallback.
    • Each image is test-loaded before use.
    • Photos are cached for 30 days.
    • YouTube channel avatars are avoided as the main source because their links expire.
  • Artist names are normalised before comparing, so the same artist always matches:
    • accents are folded and "&" is read as "and";
    • " - Topic" and "feat." are stripped;
    • "P!nk" equals "Pink".
  • Response cache (core/cache.ts): answers are saved in local storage with an expiry time.
    • Anything holding Google-signed image links expires after 6 hours; lyrics after 30 days.
    • Old entries are trimmed.
    • If storage is ever full, the cache is pruned first, so it can never block saving your history or queue.

Chapter 12·Platform

Accounts and sync#

Signing in#

  • Android: the native Google account picker (@capacitor-firebase/authentication). Its ID token is handed to Firebase.
  • Web: Google Identity Services' own button, exchanged the same way.
  • An ID token is a signed proof of who you are.
  • Firebase code is loaded only when needed, so a local-only install never loads it.
  • Offline, the last signed-in identity is remembered, so downloads stay reachable.

The cloud document#

Each user has one Firestore document, users/{uid}:

FieldContents
profilename, avatar colour, created date
historyup to 600 plays
tastethe computed taste profile
playCountlifetime plays
listeningStatsmonthly rollups, one section per device
likedIds, likedTrackMeta, followedArtists, dismissedTrackIdsthe library
playlistsfull playlists, including a shrunk cover photo
updatedAtwhen it last changed

Security rule (set in the Firebase console): you can only read or write your own document:

How data travels#

  • Web/desktop uses the Firestore web SDK with a live listener.
  • Android uses Firestore's REST API through native HTTP. The SDK's own connection broke when Capacitor redirected the browser's networking.
    • Each write names exactly the fields it changes (an update mask) and carries a precondition: "only if the document hasn't changed since I last saw it".
    • If another device changed it meanwhile, the app pulls, merges and tries again, so a sleeping phone can't overwrite newer changes.
    • Every 10 s while visible, it checks only the updatedAt field, and pulls the full document only when another device wrote. It pauses while hidden.
  • Batching (coalescedSync.ts):
    • Only fields that actually differ are sent.
    • Your own edits go out after 0.5 s.
    • Play-driven changes (history, stats, taste) wait up to 10 minutes, and are sent at once when the app goes to the background or you sign out.
    • Failures back off, up to a minute.

Safety rails#

  • The hydration gate. Nothing is written to the cloud, and onboarding is never shown, until this device has confirmed the account's cloud state. A fresh or empty device can therefore never wipe your real data. If confirming fails within 12 s, the sync-error screen offers a retry.
  • Merging, not overwriting:
    • likes, follows and hidden songs use a three-way merge, so a removal made on this device isn't undone;
    • playlists keep the newer version of each;
    • history merges by play;
    • stats merge per device.
  • The account boundary (accountBoundary.ts) remembers which account owns the local data. It was added after a real leak, where account B saw account A's playlists and history on the same phone.
    • Signing in as a different account resets all account data first.
    • Signing out: finish recording the current play, stop music, send pending changes (with a time limit), then reset.
    • Device-level things are kept: theme, downloads, caches and refresh rate.
  • Local-first trade-off: a deletion on another device reaches this one only after that device's change arrives. That is deliberate, because silent data loss here would be worse.

During development, Vite forwards /yt-api, /ytm-api, /deezer-api and /better-lyrics-api to the real services. Browsers block direct calls to them (CORS, section 20). On the phone, native HTTP avoids CORS altogether.

scripts/patch-android.mjs#

It runs after every cap add android, in CI and locally. It is idempotent (running it twice changes nothing more), and it stops loudly if the generated files ever change shape. It:

  • turns on native Google sign-in;
  • adds the permissions, the maker-app <queries>, the deep link and the Media3 service declaration;
  • adds Kotlin, Media3 1.11.1 and coroutines to the build;
  • copies the plugins and vector drawables, and registers the three plugins;
  • adds the renderer-crash listener and the splash/icon settings;
  • patches the Firebase sign-in plugin so sign-out clears both Google sessions;
  • stamps the version from package.json. versionCode = major×10000 + minor×100 + patch, so 1.2.4 → 10204.

The CI build (.github/workflows/android.yml)#

On every push to main (or a manual run), GitHub's servers:

  1. Install Node 22, read the version, and install packages (npm ci).
  2. Build the web app with the secret keys, without source maps.
  3. Create the Android project, generate icons, and write google-services.json from a secret.
  4. Patch, then cap sync.
  5. Install Java 21 and restore the stable signing key from a secret. It must stay the same so that Google sign-in (which is tied to the key's SHA-1 fingerprint) keeps working and updates install over older versions.
  6. gradlew assembleRelease, then align and sign the APK.
  7. Verify the signature and print the fingerprints.
  8. Upload utopia-v1.2.4-<commit> as a downloadable artifact, kept for 30 days.

You don't need Android Studio: push, wait for the run, download the APK from the Actions page, and install it on the phone.

Where the version appears#

  • package.json is the single source (npm mirrors it into package-lock.json).
  • The Android build number is stamped from it.
  • It appears in the CI artifact name.
  • In the app, it shows twice in phone Settings: the About card and the footer (v1.2.4).

Testing and verification#

In the repository:

  • TypeScript type checking, which is part of every build and the only automatic gate in CI.
  • npm run test:media-fetch, which proves a partial download can never be accepted.
  • A manual Playwright smoke test (test-run.mjs).

  • Stats: rollups, per-device merging and summaries.

Known limitations and open items#

  • YouTube doesn't play through a plain web <audio> element. Browsers block the links (Opaque Response Blocking), and YouTube's CDN refuses non-browser proxies. The web uses YouTube's embedded player instead; the Android app is the real target.
  • Nothing from the September 2026 playback and heat work has been verified on a phone yet. See the checklist in section 18.
  • The desktop layout lacks the Stats page and the full Settings page. Its adaptation is tracked in DESKTOP_FOLLOW_UP.md.
  • Navidrome support exists but isn't wired into any screen. The soundcloud and cloud source ids have no code behind them.
  • Downloads belong to the device, not the account. Another account signed in on the same phone sees the same downloads.
  • Reinstall restore limits:
    • .webm downloads (rare, used only when a video has no MP4 audio) count as video to Android, so the music permission can't see them after a reinstall;
    • covers and lyrics come back only once you're online.
  • Better Lyrics (word timing) is unavailable in the web build.
  • No playlist rename in the UI yet (the store supports it).
  • Firestore rules live only in the Firebase console, not in the repository.
  • Release 1.2.4 was checked before pushing:
    • type check;
    • production build;
    • the media-fetch, queue, stats, sync and downloads-restore suites;
    • the Kotlin compile;
    • two runs of the patch simulation.
